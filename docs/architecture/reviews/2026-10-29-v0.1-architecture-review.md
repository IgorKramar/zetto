## Статус

Это техническая проверка, приёмка версии владельцем остаётся отдельной.

## Сводка

Один Cargo package реализует CLI/JSON и минимальный TUI поверх общих операций.
Главный риск — согласованность нескольких файлов при сбое; состояние операции,
предыдущая версия и рабочая копия сохраняются в самом vault.

## Соответствие ADR

| Решение | Результат |
|---|---|
| ADR-0001 | Имя package/binary — zetto. |
| ADR-0002–0004 с уточнениями ADR-0005 | ULID/frontmatter, имена и ссылки проверяются; чтение не меняет файлы; unknown YAML сохраняет значения. Исторические auto-rename/alias-tiebreak не реализованы. |
| ADR-0005 | `format` не знает ФС; `resolver` один для каталога и проверки публикации; неоднозначность не выбирает первый файл. CLI/TUI получают одинаковые rule IDs. |
| ADR-0006 | `vault` владеет путями, OS-lock, no-clobber, hash/backup и recovery. План сохраняется до подготовки payload; подготовка, перенос и откат возобновляются по фактическим файлам. Блокировка не удерживается во время редактора. |
| ADR-0007 | `cli`/`tui` вызывают `app`, не друг друга; `app` не зависит от terminal/stdout. Синхронная сверка в v0.1 допустима; очередь фоновой работы и палитра действий относятся к следующим версиям. |
| ADR-0008 | Capture сохраняет inbox без связи; publish проверяет структуру, заголовок и граф; root-исключение задаёт `.zettorc`. Отказ new сохраняет draft; редактор сохраняет конфликтующие версии. |

`editor` запускает argv с рабочей копией, `config` отделяет vault от локальных
настроек. Прямой `sync_all` рабочей копии в `app::edit` подтверждает результат
внешнего редактора; изменение заметки выполняется через `vault::finish_edit`.
SQLite, daemon, async runtime и интерфейсы для единственной реализации не введены.

## Блокирующие замечания

Архитектурных конфликтов с принятыми ADR не обнаружено.
Локальная корректность и тесты проверяются отдельным ревью кода.

## Неблокирующие предложения

suggestion: при внедрении SQLite в v0.2 сохранить файловый ключ отдельно от
ULID и заменить поиск целей по полному каталогу. Текущее ограничение отмечено
в коде; заранее строить второй индекс в v0.1 не требуется.

## Вопросы

Новых архитектурных решений для принятого объёма v0.1 не требуется.
Бюджеты масштаба и полная платформенная матрица пока не подтверждены.

## Сильные стороны

Проверки публикации и защиты файлов не дублируются в интерфейсах.
Recovery не зависит от будущего удаляемого индекса; PTY проверяет настоящий
терминальный жизненный цикл, а не только состояние Rust-объектов.
