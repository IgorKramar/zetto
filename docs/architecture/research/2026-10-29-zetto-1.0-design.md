# zetto 1.0 — архитектура и путь к выпуску

Дата: 2026-10-29. Автор: Igor Kramar.

**Статус: предложение для обсуждения, не принятый ADR.** Описывает рекомендуемое готовое приложение. Не утверждает, что перечисленные возможности уже реализованы. Принятые ADR-0001–0004 и текущие `ARCHITECTURE.md` / `STRATEGY.md` этим документом не изменяются. Для несовместимых уточнений ниже явно указаны необходимые новые ADR.

## 1. Продукт, который выпускаем

zetto — приложение для личной связанной базы знаний: красивый, быстрый TUI для ежедневной работы и полноценный CLI для скриптов. Один Rust-бинарник; Markdown на диске; без сервера, аккаунта и обязательных сетевых соединений. Основная платформа — Linux, включая tmux и SSH; macOS входит в проверяемый выпуск 1.0. Windows до подтверждения полного терминального и файлового контракта остаётся экспериментальной платформой, а не скрытым обещанием совместимости.

Полный ежедневный цикл: быстро записать мысль → обработать черновик → найти существующую заметку → связать → опубликовать → вернуться через поиск и обратные ссылки. TUI — основной интерактивный интерфейс. CLI — равноправный способ выполнять те же операции. Пользователь может работать каждым отдельно.

Границы 1.0: один корень хранилища на запуск; один автор с несколькими локальными процессами; локальная файловая система. Несколько независимых хранилищ допустимы через `--vault`, но объединённого графа между ними нет. Синхронизацией и историей управляет пользователь через git. Постоянного демона, сетевого API, LSP, собственного полнотекстового редактора и загрузчика сторонних расширений в 1.0 нет.

### Обязательный результат 1.0

| Область | Готовое поведение |
|---|---|
| Заметки | Создание, чтение, редактирование в `$EDITOR`, переименование заголовка с сохранением ID, теги, ссылки |
| Быстрая запись | Надёжное сохранение в inbox без требования немедленно найти связь |
| Обработка | Выбор связи и публикация с проверками; неудача оставляет черновик |

| Проверка | Единые диагностики в TUI, CLI и JSON; отдельный режим проверки всего хранилища |
| Данные | Восстановление после прерывания записи, явные конфликты, пересоздаваемый индекс |
| Внешние инструменты | `$EDITOR`, stdout/stdin, машинный вывод, completion, инструкции для fzf/rg/git |

| Выпуск | Установка бинарника или через Cargo, справка, примеры, проверка обновления и совместимости |

## 2. Варианты архитектуры

| Вариант | Преимущества | Цена и граница применимости | Оценка объёма |
|---|---|---|---|
| A. Развивать прототип из истории: граф в памяти, полный обход при запуске | Быстрее получить первый работающий экран; минимум состояния | CLI платит за разбор каждого файла; прототип предшествует ADR; переделка правил хранения и UI остаётся | Недели до спайка, месяцы до полноценного 1.0 |
| B. Один бинарник: общее ядро, файлы и производный SQLite-индекс | Независимый CLI, быстрый повторный поиск, TUI без серверного жизненного цикла | Нужны сверка файлов с индексом и координация записей | Несколько месяцев; выбранный вариант |
| C. Демон владеет графом; CLI/TUI обращаются через IPC | Общая горячая память и одна очередь записи для всех клиентов | Протокол, запуск/перезапуск сервиса, несовпадение версий, недоступность сервиса; внешние редакторы всё равно меняют файлы мимо него | Дополнительные недели инфраструктуры и постоянная стоимость сопровождения |

| Критерий | A | B | C |
|---|---|---|---|
| Скорость появления спайка | Хорошо | Средне | Плохо |
| Частые независимые CLI-запуски | Плохо | Хорошо | Хорошо |
| Работа без фонового процесса | Хорошо | Хорошо | Плохо |
| Простота установки и диагностики | Хорошо | Хорошо | Средне |
| Сложность для одного разработчика | Средне | Хорошо | Плохо |

**Рекомендация — B.** В 1.0 достаточно общего ядра внутри процесса и общего пересоздаваемого индекса. Исторический код полезен как источник сценариев, но его структура и зависимости не переносятся автоматически.

Журнал событий файловой системы как источник истины не выбираем: vim, git и другие инструменты пишут без участия zetto, а события наблюдателя могут теряться. Журнал незавершённых операций самого zetto ниже нужен только для восстановления записей; это не event sourcing графа.

Electron противоречит принятой стратегии; отдельная графовая БД не нужна для обхода соседей; CRDT не оправданы личным локальным хранилищем; собственный Markdown-парсер создаёт ненужную совместимость; принудительный запуск fzf внутри каждого TUI-поиска затрудняет единый интерфейс. Ни один из этих вариантов не входит в план.

Пересмотр B оправдан, если появится реальная потребность в постоянно работающих внешних клиентах или измерения покажут, что открытие индекса и сверка файлов доминируют даже после оптимизации. Размер хранилища сам по себе ещё не основание вводить демон.

## 3. Устройство приложения

Схема компонентов: [c4-l3-zetto-1.0-proposal.md](../diagrams/c4-l3-zetto-1.0-proposal.md).

Начинаем **с одного Cargo package**, `src/lib.rs` и `src/main.rs`, без набора микрокрейтов. Границы — модули и направленность зависимостей, а не количество манифестов.

| Модуль | Ответственность | Что ему запрещено |
|---|---|---|
| `note` | ULID, разобранная заметка, ссылки с координатами, теги, диагностики | SQL, terminal I/O, запуск процессов |
| `format` | Границы frontmatter, YAML, поток Markdown-событий, каноническая запись | Решать, где лежит хранилище или как выглядит экран |
| `vault` | Пути, чтение, блокировки, безопасная запись, восстановление | Рисовать интерфейс, владеть поисковой выдачей |
| `index` | SQLite, сверка файлов, разрешение ссылок, поиск, граф | Быть единственной копией пользовательских данных |
| `app` | Операции Capture/New/Edit/Publish/Retitle/Link/Lint/Import/Export | Зависеть от TUI, stdout или клавиатуры |
| `cli` | clap, stdin/stdout/stderr, форматы вывода и коды завершения | Дублировать операции `app` |
| `tui` | Состояние экранов, действия, отрисовка, очередь фоновых задач | Прямо переписывать файлы или выполнять SQL |
| `editor`, `config` | Запуск редактора и загрузка настроек | Скрыто исполнять команды из чужого хранилища |

CLI и TUI вызывают функции `app` с одинаковыми типизированными параметрами. TUI не запускает собственный бинарник как подкоманду для обычных действий. Отдельный процесс нужен редактору и явно вызванному внешнему инструменту.

Не вводим интерфейс для каждого модуля. Конкретные функции и структуры достаточны. Чистые проверки тестируются без диска; настоящие файловые операции — во временных каталогах, без имитации файловой системы.

### Технологии

| Задача | Выбор |
|---|---|
| CLI | `clap`, генерация completion и man page из определения команд |
| TUI / терминал | `ratatui` + `crossterm` |
| Markdown | `pulldown-cmark`, включая `ENABLE_WIKILINKS`; диапазоны исходного текста для диагностик |
| YAML | Кандидат `serde-saphyr` после проверки корпуса совместимости; явный пересмотр зависимости из ADR-0002/0004 |
| Индекс | `rusqlite` с SQLite, встроенной в бинарник, и включённым FTS5 |
| Наблюдение за файлами | `notify`; при необходимости периодический обход |
| Быстрый выбор заголовка | `nucleo-matcher`; небольшой ограниченный список кандидатов, без собственного нечёткого алгоритма |
| Данные и настройки | `serde`, `serde_json`, TOML, `ulid`, `slug`; существующие принятые правила ID/slug сохраняются |
| Фоновые операции | Потоки стандартной библиотеки и ограниченные очереди; без Tokio до появления задачи, которой он необходим |

Это выбор библиотек, а не утверждение об их версиях совместно с MSRV. До первого `Cargo.toml` проверяется минимальный поддерживаемый Rust всего набора; сохраняется lockfile приложения. Не наследуем версии 2024 года из спайка.

Официальная документация подтверждает поддержку wikilinks у [pulldown-cmark](https://docs.rs/pulldown-cmark/latest/pulldown_cmark/struct.Options.html), возможности [rusqlite](https://github.com/rusqlite/rusqlite) и нечёткое сопоставление у [nucleo](https://docs.rs/nucleo/latest/nucleo/). Выбор выше — проектная рекомендация, а не результат измерения быстродействия zetto.

## 4. Контракт хранения

Предлагаемая раскладка:

```text
my-vault/
  .zettorc                    # переносимые настройки и версия хранилища
  <ULID>-<slug>.md             # опубликованные заметки прямо в корне
  inbox/                      # первичные пользовательские данные: черновики
    <ULID>-<slug>.md
  assets/                     # вложения, обычные относительные Markdown-ссылки
  .zetto/
    recovery/                 # планы незавершённых операций и резервные версии
    locks/                    # локальная координация процессов
```

Корень и `inbox` разделяют этапы обработки, а не тематики. Опубликованные заметки лежат плоско прямо в корне; сканер читает Markdown верхнего уровня и отдельно `inbox`, не обходит `assets` и `recovery` как заметки. Это предлагаемое решение A4, которого пока нет в принятых ADR. Путь хранилища по умолчанию сохраняется из ADR-0001: `~/.zetto/notes/`; вложенного `notes/notes` не возникает.

Индекс, UI-состояние и логи находятся в локальных XDG-каталогах, а не рядом с синхронизируемыми заметками. Ключ экземпляра хранилища — хеш канонического абсолютного пути. Перенос хранилища создаёт новый индекс, но не меняет заметки. SQLite WAL остаётся на локальном диске, даже если пользователь держит файлы на другом томе. Сетевые файловые системы не входят в гарантию корректности 1.0.

В git рекомендуем хранить `.zettorc`, заметки в корне, `inbox`, `assets`. `recovery` содержит пользовательские данные и входит в резервное копирование, но не коммитится автоматически. `locks` исключается. Нельзя помечать весь `.zetto` как удаляемый кэш: данные восстановления имеют другой жизненный цикл. В 1.0 автоматического удаления recovery нет: `doctor` показывает размер и незавершённые операции; очистка выполняется по явному плану после проверки. Это сознательная цена простого восстановления: резервные версии занимают дополнительное место и не заменяют независимый backup.

### Формат заметки

Сохраняем ADR-0002–0004: ULID каноничен во frontmatter; filename повторяет ID и содержит slug; `id` и `title` обязательны; ссылки, создаваемые zetto, — `[[ULID]]` / `[[ULID|текст]]`. `tags`, `aliases`, `created`, `updated` необязательны. Неизвестные поля не удаляются. Текст заметки при изменении метаданных не переформатируется.

Черновик использует тот же формат. Временный пустой заголовок разрешён только в процессе создания и в inbox; публикация требует заголовок. Состояние draft определяется расположением в `inbox`, поэтому не вводим обязательное поле, несовместимое с ADR. Обрабатывается весь inbox независимо от возраста заметки.

Вложения — скопированные по явному действию файлы в `assets`; абсолютные пути и автоматическая загрузка URL не нужны. TUI показывает имя/тип/размер и открывает файл только явным действием. Отображение изображений терминальными протоколами не требуется для 1.0.

### Версии

Версии разделены: версия бинарника, версия формата заметки, версия конфигурации хранилища, версия SQLite-схемы, версия машинного вывода. Изменение таблиц индекса не требует переписывать Markdown.

`format-v1` не добавляет обязательное `format: 1` в каждую заметку — это соответствует текущим ADR. Версия хранилища записана в `.zettorc`; отдельно читаемая заметка без версии трактуется как v1. Неизвестная старшему бинарнику мажорная версия хранилища запрещает изменения, сохраняя возможность явного чтения raw-файлов.

До публичного beta публикуем `docs/format-v1.md` и корпус примеров. Уточняем: добавление необязательного поля не ломает формат, но изменение значения существующей ссылки или обязательности поля может ломать поведение. Для такого изменения нужен новый ADR и мигратор. Лицензия спецификации выбирается явно при её публикации, не выводится автоматически из MIT-лицензии кода.

## 5. Целостность файлов и параллельная работа

### Запись одного файла

1. Получить кратковременную межпроцессную блокировку управляемых изменений этого хранилища. Не держать её, пока человек печатает в редакторе.
2. Перечитать файл и сравнить хеш исходных байтов с версией, на которой основано изменение. При конфликте сохранить предложенную версию отдельно и вернуть диагностируемый конфликт.
3. Для перезаписи существующего файла сохранить предыдущую версию в `recovery`; подтвердить её запись до замены оригинала. Для сложной операции сохранить план и ожидаемые хеши.
4. Записать временный файл в том же каталоге, выполнить flush/fsync, атомарно заменить целевой файл; подтвердить запись каталога там, где это поддержано. При создании запретить замену существующего файла.
5. Обновить производный индекс транзакцией SQLite.
6. Если индекс не обновился, вернуть **успех сохранения файла** с предупреждением `index_stale`. Не заставлять пользователя повторять создание уже сохранённой заметки.

Блокировка координирует процессы zetto, но не vim и git. Проверка хеша сужает окно гонки, однако не превращает внешний редактор в участника транзакции. Поэтому обещание формулируется точно: zetto не отбрасывает уже принятый им текст молча; обнаруженные конфликты сохраняются; произвольную параллельную запись стороннего процесса гарантировать невозможно.

### Редактор

Для существующей заметки `zetto edit` создаёт устойчивую рабочую копию в `recovery`, запоминает базовый хеш, отдаёт копию редактору. После выхода проверяет содержимое и применяет его к оригиналу по протоколу выше. При ошибке запуска/аварии редактора/конфликте рабочая копия остаётся. Исходный файл до подтверждённой записи не меняется. TUI восстанавливает terminal/raw mode до запуска редактора и повторно инициализирует после; длинное редактирование не блокирует другой CLI.

Относительные пути внутри копии не разрешаем от каталога `recovery`: рабочий каталог процесса — корень хранилища, zetto-операции над ссылками используют исходное расположение заметки. Интеграции редактора, зависящие от физического пути текущего файла, потребуют адаптера; прямой `vim file.md` остаётся допустимым внешним редактированием с более слабой защитой. Это сознательный компромисс, который проверяется на реальном ежедневном сценарии до beta.

Конфигурация редактора поддерживает массив аргументов. `$VISUAL` / `$EDITOR` разбираются как команда с аргументами без запуска shell. Имя заметки всегда отдельный аргумент. Для GUI-редакторов пользователь явно задаёт аргумент ожидания. Команды из файла, полученного вместе с чужим хранилищем, автоматически не исполняются.

### Операции над несколькими путями

Публикация из inbox, retitle, импорт и миграция имеют записанный на диск план: operation ID, исходные/целевые пути, ожидаемые хеши, резервные копии, завершённые шаги. После каждого шага обновляется след. SQLite не используется как единственное место хранения этого плана.

Предпочитаем последовательность, при которой прерывание оставляет полную старую или полную новую копию. Если после сбоя видны два файла с одним ULID, они помечаются как неоднозначность; нельзя автоматически выбирать «самый свежий». `zetto doctor` показывает план и предлагает продолжить либо восстановить исходные данные. Повторное выполнение должно распознавать уже выполненные шаги.

Нет обещания общей атомарности нескольких файлов и SQLite. При запуске обнаруживается незавершённая операция; чтение доступно с предупреждением, новые изменения блокируются до разрешения затронутой операции. Полный rebuild индекса восстанавливает только производные данные, не заменяет восстановление файлов.

Чтение и поиск не переименовывают и не переписывают заметки. Несоответствие slug заголовку показывается диагностикой; исправление — `retitle` или явный `resync --apply`. Изменение `updated` после внешнего редактирования выполняется только явным управляемым действием, а не из наблюдателя. Механизм автоматического `updated` в ADR-0004 требует уточнения новым ADR.

## 6. Индекс, разрешение ссылок и поиск

### Модель SQLite

| Таблица | Существенные данные |
|---|---|
| `files` | Внутренний file key, уникальный относительный путь, обнаруженный ULID, заголовок, stage, размер, mtime, хеш, статус разбора |
| `links` | Исходный file key, исходный target, тип ссылки, диапазон байтов, разрешённый target file key либо причина unresolved |
| `tags`, `aliases` | Значения и file key; индексы по нормализованному значению |
| `diagnostics` | Правило, уровень, путь, диапазон, сообщение, допустимое исправление |
| `notes_fts` | Заголовок и тело для FTS5 |
| `meta` | Версия схемы, generation, сведения о последней сверке и полноте |

**ULID не является первичным ключом `files`.** Иначе два файла с одним ID нельзя представить и диагностировать. Валидный граф строится по однозначному сопоставлению ID → файл. Неоднозначности, ошибочный YAML и отсутствующие поля видны в интерфейсе и `lint`, а не исчезают из хранилища.

Текст для предпросмотра читается из файла по выбранной заметке; не держим тела всех заметок в памяти. Индекс содержит производную копию текста для поиска и поэтому тоже конфиденциален; его локальный каталог имеет ограниченные права. Никакого автоматического отправления диагностик или содержимого в сеть.

### Свежесть без демона

- При обычном CLI-запросе выполнить обход управляемых каталогов и сверить размер/mtime/наличие с `files`; разобрать изменившееся и закончить транзакцию перед выдачей результата.
- Это **O(N) stat-операций**, а не O(1). Оно избегает повторного разбора каждого тела, но не стоимости обхода. Эту стоимость измеряем отдельно.
- `--fresh` перечитывает и хеширует все файлы; нужен после переноса с сохранёнными временными метками и для проверки полной согласованности. Одинаковые размер/mtime сами по себе не доказательство неизменности.
- `--cached` явно разрешает быстрый ответ без сверки и помечает его как cached. Никакого скрытого обещания «индекс всегда актуален».
- TUI может показать последнюю выдачу сразу с индикатором сверки; после сверки обновляет generation. Проверка перед публикацией перечитывает изменяемую заметку и целевые файлы, не полагается на старый экран.
- `notify` сообщает, что часть дерева надо проверить. События объединяются; переполнение очереди переводится в флаг полного обхода. Дополнительно сверка при возврате фокуса и периодически в активном TUI; полного постоянного сканирования на каждом кадре нет.
- При изменении/удалении цели повторно разрешаются входящие ссылки. Для alias/filename-изменения заново проверяются затронутые разрешённые и неразрешённые targets; при большом наборе — полный проход resolver. Не оставляем старые backlinks после rename.

Generation обозначает согласованную транзакцию индекса, а не атомарный снимок внешней файловой системы. Если файл меняется во время чтения, проверка его состояния до/после обнаруживает гонку и повторяет чтение ограниченное число раз; постоянно меняющийся файл помечается нестабильным. Даже `--fresh` не может остановить внешний vim или git: он гарантирует полный проход с проверкой содержимого, а не отсутствие изменений после него.

Документация [notify](https://docs.rs/notify/latest/notify/) отдельно описывает различия событий у редакторов и ограничения больших/сетевых каталогов. Поэтому наблюдатель ускоряет сверку, но не доказывает корректность индекса.

### Конкурентный индекс

SQLite в WAL-режиме, отдельные соединения для чтения и короткие транзакции записи. Один процесс не держит write transaction во время редактирования, сканирования всего диска или ожидания клавиши. Для обновления общего индекса процессы берут отдельную короткую блокировку; при необходимости повторяют сверку после её получения. Изменения графа и FTS публикуются одной generation.

`SQLITE_BUSY` обрабатывается ограниченным ожиданием, затем понятной ошибкой/явно разрешённым cached-ответом. Удалять используемую другими процессами SQLite-базу нельзя: rebuild меняет её содержимое под блокировкой. Карантин повреждённого индекса требует исключительного доступа; при занятом индексе чтение raw-файла всё равно доступно.

WAL не означает отсутствие всех блокировок; это прямо отмечено в [документации SQLite](https://www.sqlite.org/wal.html). При сборке проверяем, что встроенная SQLite содержит исправление WAL-reset bug: документация указывает 3.51.3+ либо соответствующие backport-версии. Это проверка реального `sqlite_version()`, а не только версии `rusqlite`.

### Разрешение ссылок

Один resolver для графа, предпросмотра, lint и export. Основной путь — строгий канонический ULID через проверку `ulid`, а не самодельное декодирование части timestamp. Далее — совместимые пути, aliases и импортированные имена по явно опубликованному порядку.

Дубликат ULID всегда неоднозначен. Коллизия alias по умолчанию показывает кандидатов и требует выбрать ULID при создании ссылки; чтение такой ссылки помечается unresolved/ambiguous. Автоматический выбор «первого по времени» из ADR-0004 предлагается отменить новым ADR: ошибка выбора знания хуже явного предупреждения. Alias — удобство импорта и чтения, zetto всегда создаёт ссылки с ULID.

Ссылки внутри code spans/blocks не образуют граф. Отсутствующий, неоднозначный или неподдерживаемый target отображается буквально с диагностикой. В 1.0 не включаем embeds, anchors и block references без отдельного решения, как предписывает ADR-0003. Внешний URL не становится ребром графа. Открытие внешнего URL — только по явной команде и ограниченному списку допустимых схем.

### Поиск

Три разные задачи, без смешения обещаний:

1. **Быстрый переход:** нечёткое сопоставление заголовков/aliases, дополнительный вес недавним и точным совпадениям, результаты обновляются при вводе. Это не полнотекстовый поиск.
2. **Полнотекстовый поиск:** SQLite FTS5, `unicode61`, отдельные веса заголовку и телу. Русский текст индексируется как слова; автоматическое русское склонение/лемматизация не обещается. Пунктуация обычного запроса экранируется. Расширенный FTS-синтаксис доступен только явно.
3. **Буквальная подстрока/regex:** `search --literal` / `--regex`; проверенный потоковый поиск по файлам с ограничением времени/отменой. `rg` можно вызвать явным флагом как ускоритель, но он не является runtime-зависимостью. На чистой установке работает встроенный путь.

Для небольшого проекта regex-путь можно реализовать через библиотеку `regex`; не поддерживать произвольные regex-движки или выполнять регулярные выражения через shell. Ограничения размера файла/результата объявлены и дают диагностику, не молчаливое исключение заметки.

FTS5 — поиск токенов, не универсальный fuzzy/substring-движок; его возможности и tokenizers описаны в [документации SQLite](https://www.sqlite.org/fts5.html). Отдельный Tantivy-индекс или trigram-индекс вводится только после измеренного провала целевых запросов.

## 7. Быстрая запись и методология

Разделяем две операции, сохраняя обе в одном приложении:

**Capture:** принять текст, выдать ULID, сохранить черновик в inbox, подтвердить путь. Ссылка не нужна. Изменение не ждёт полной сверки графа. Даже при ошибке последующих проверок текст уже сохранён. TUI поддерживает небольшое поле быстрого ввода с многострочной вставкой; длинный текст отправляется в редактор.

**Publish:** проверить заголовок, ID, соответствие имени, корректность ссылок и наличие хотя бы одной разрешённой исходящей ссылки на другую опубликованную заметку; затем перенести черновик из inbox в корень. Ссылка на себя, URL или ещё один черновик не считается выполнением требования. Обработка доступна и через TUI inbox, и через CLI.

**New:** удобный составной сценарий: создать черновик → при необходимости открыть редактор → выбрать ссылку → опубликовать. Если проверки не пройдены, остаётся черновик с сообщением о причине. Ничего из написанного не отбрасывается.

Пустое хранилище не заставляет создавать фиктивную связь. `init` предлагает одну корневую заметку и записывает её ID в переносимую конфигурацию. Только она исключена из требования исходящей связи; она остаётся обычным Markdown-файлом. Исключение видно в lint. Дополнительные исключения — явная конфигурация, а не автоназначение роли «корень» любой сироте.

### Проверки

Движок — список встроенных функций/enum правил и единый `Diagnostic`, без динамических плагинов. Диагностика содержит rule ID, уровень, путь, диапазон, объяснение и возможное исправление. Правила запускаются над заметкой и графовым снимком. Отдельно задаются структурная валидность, методологические предупреждения и условия публикации.

- Невалидный ID, дубликат, опасный путь, невозможный разбор для управляемой записи — блокируют изменение; эти защиты нельзя отключить пресетом.
- `link-before-save` трактуется как `link-before-publish`. По умолчанию блокирует публикацию, но не сохранение черновика. Смена смысла имени правила фиксируется в ADR, не маскируется UI.
- «Atomic note» нельзя надёжно доказать количеством символов. Размер — советующее правило, а не претензия на семантическую проверку одной мысли.
- `--fix` применяет только однозначные локальные исправления после вывода плана. Связи между мыслями, заголовки и слияние дубликатов не генерируются автоматически.
- Изменяемые уровни `off/info/warn/error`, встроенные пресеты `recommended-luhmann` / `lenient`; исключение на заметку — отдельное `x-zetto-lint` с перечислением правил и причиной. Структурные защиты остаются обязательными.

Существующую опубликованную заметку после ручной правки можно сохранить даже с новой методологической проблемой: текст не теряется, граф показывает диагностику. Иначе пользователь обходил бы приложение через vim и получал два несовместимых мира.

### Метрики

Нынешняя цель «связанная заметка за 5 секунд, включая мышление» плохо отделяет скорость приложения от работы человека. Предлагается изменить STRATEGY отдельным решением:

- Capture: время от подтверждения ввода до надёжного сохранения, плюс отдельный пользовательский сценарий «готовая короткая мысль → inbox».
- Publish: системное время обработки отдельно от времени выбора осмысленной связи.
- Доля сирот: среди опубликованных заметок, исключая явно назначенный root; inbox считается отдельно, не скрывается из отчётов.
- Размер/возраст inbox и время до публикации: защита от «метрика сирот хорошая, потому что всё навсегда осталось черновиками».
- Плотность ссылок — диагностический показатель, а не требование добавлять бессмысленные ссылки ради числа.

Это изменение трактовки продуктовых метрик, а не доказанная победа над исходным требованием.

## 8. TUI: визуальный характер и поведение

Визуальное направление — тёплая тёмная палитра на основе Gruvbox: фон `#282828`, поверхность `#32302f`, текст `#ebdbb2`, приглушённый `#a89984`, акцент `#d8a657`, связь `#89b482`, ошибка `#ea6962`. Это проектные токены темы, не зависимость от конкретного терминального оформления пользователя. Доступны светлая и монохромная темы, пользовательский TOML и прозрачный фон.

Оформление: тонкие линии, ровные отступы, спокойный заголовок `ゼ zetto`, один яркий акцент на фокусе, минимум вложенных рамок. Читаемый текст важнее обилия символов. Nerd Font — опция, ASCII/обычный Unicode работает из коробки. Анимация нужна только для конечных состояний вроде индексации, выключается настройкой. Постоянного декоративного 60 FPS-цикла нет.

```text
 ゼ zetto   personal                           / поиск    Ctrl-P команды
 ─────────────────────────────────────────────────────────────────────
  БИБЛИОТЕКА       ЗАМЕТКИ                  Одна мысль — одна заметка
  Все       842    › Одна мысль...           ─────────────────────────
  Inbox       7      Связи и контекст       Короткая формулировка
  Недавние           Как искать...         своими словами.
  Избранное          Зачем нужен ID
  Проверки    3                            → Связи и контекст
                                            → Зачем нужен ID
  ТЕГИ
  rust                                      ОБРАТНЫЕ ССЫЛКИ
  knowledge                                 От заметок к аргументам
 ─────────────────────────────────────────────────────────────────────
  NORMAL   842 notes · 7 drafts    индекс актуален     n новая e править
```

Макет схематичный; ширина текста рассчитывается терминальными ячейками, не байтами Rust-строк.

### Основные представления

1. **Library:** слева коллекции/теги, в центре выдача, справа Markdown-предпросмотр; обратные ссылки под текстом или в контекстной панели.
2. **Focus:** чтение одной заметки с историей переходов и выбором ссылок с клавиатуры; удобен для узкого окна.
3. **Inbox:** черновик, предпросмотр, кандидаты связей, причины невозможности публикации; одно действие «Опубликовать».
4. **Graph:** локальное окружение выбранной заметки, направления рёбер и компактное дерево соседей; переход на узел открывает заметку. Глобальный силовой граф из тысяч точек не нужен для 1.0.
5. **Diagnostics:** ошибки группируются по правилу/файлу; Enter ведёт к проблеме, действие исправления показывает эффект.
6. **Command palette / Help:** все пользовательские действия с текущими клавишами, поиском и пояснениями; не отдельная система команд.

История переходов, выделенная заметка, ширина панелей и избранное сохраняются в локальном UI-state и не меняют Markdown. Избранное 1.0 локально; его синхронизация потребовала бы отдельного переносимого формата.

### Управление

- `j/k` и стрелки — перемещение, `Enter` — открыть, `Esc` — вернуться/закрыть слой.
- `Tab` / `Shift-Tab` — фокус панелей; `h/l` могут дублировать переключение, но не нужны для доступа.
- `/` — поиск, `Ctrl-P` — палитра, `?` — справка.
- `n` — новая заметка с обработкой, `c` — быстрая запись, `e` — редактор, `l` — добавить связь, `g` — локальный граф.
- В inbox `p` — публикация; конфликтующие клавиши зависят от контекста и показываются в подсказке.
- В текстовом вводе символы не трактуются как навигация. Команды разрешаются по контекстам `global/library/reader/inbox/input/modal`; ошибочные или недостижимые привязки диагностируются при загрузке.

Изменение клавиш работает через типизированный `Action`, общий для клавиатуры и палитры. Мышь дополняет выбор и прокрутку. Каждое действие доступно с клавиатуры. Потеря цвета не лишает смысла: ошибка имеет текстовый знак и сообщение, фокус — маркер и стиль.

### Размеры и терминальные возможности

- От 120 колонок — три области; 80–119 — две; 60–79 — одна с переключением списка/текста; ещё меньше — минимальный список или понятное сообщение о размере.
- `--color=auto|always|never`, поддержка `NO_COLOR` и 16/256/truecolor-палитр; явная настройка важнее ненадёжной догадки о возможностях терминала.
- Прозрачный фон включается пользователем. Не меняем палитру/заголовок/clipboard терминала без настройки.
- Clipboard: явная команда; системный провайдер либо отдельно разрешённый OSC52. Ошибка копирования не ломает приложение.
- Markdown: заголовки, списки, цитаты, код, ссылки, таблицы в пределах ширины. HTML и управляющие ANSI/OSC-последовательности из заметки не исполняются; в raw-view опасные символы видимы в экранированной форме.
- Unicode-тесты: кириллица, CJK, combining marks, emoji; корректное движение/обрезка по графемам и ширине ячеек. Терминальные расхождения отображения покрываются режимом простых символов.

### Цикл событий

Входное событие → `Action` → изменение `AppState` → задачи фонового исполнителя → результат с generation/request ID → отрисовка изменившихся областей. Функция отрисовки не читает диск и не запускает поиск.

На первом этапе: UI-поток, один рабочий поток для диска/индекса, один поток ввода. Для длинного поиска — отменяемая задача; старый результат не заменяет новый запрос. Очереди ограничены, повторные запросы поиска объединяются до последнего; переполнение событий файлов переводится в один запрос полной сверки. Снимок UI не держит SQL-транзакцию открытой.

Таймер работает только при реально меняющемся состоянии. Поиск, индексация, импорт и ошибки редактора не останавливают навигацию; TUI показывает текущую степень готовности. На Ctrl-C/обычном выходе/панике восстанавливаются raw mode, alternate screen, cursor и включённые режимы ввода. SIGKILL физически не позволяет выполнить cleanup; оставленный текст восстанавливается из файлов. Управление job control (`Ctrl-Z`/resume) проверяется отдельно на Unix.

Ratatui предоставляет [восстановление terminal/raw mode](https://docs.rs/ratatui/latest/ratatui/fn.restore.html) и описывает [варианты организации приложения](https://ratatui.rs/concepts/application-patterns/); конкретная модель очередей выше — предложение zetto.

## 9. Контракт CLI

`zetto` без команды открывает TUI только при подходящем TTY. Без TTY выводит краткую справку в stderr и ненулевой код, не включает raw mode. Интерактивные команды при перенаправленном вводе не ждут невидимого ответа. `--no-interactive` явно запрещает вопросы и открытие редактора.

```sh
zetto init ~/knowledge
zetto --vault ~/knowledge tui

printf '%s\n' 'Мысль, которую нельзя потерять' | zetto capture --stdin
zetto new --title 'Стабильные идентификаторы' --link "$note_id" --stdin < note.md
zetto edit "$note_id"
zetto publish "$draft_id" --link "$note_id"

zetto list --tag rust --format json
zetto search 'обратные ссылки' --format jsonl
zetto show "$note_id" --raw
zetto path "$note_id" --null
zetto links "$note_id" --direction incoming --format json
zetto graph "$note_id" --depth 1 --format json
zetto link "$source_id" "$target_id"
zetto retitle "$note_id" 'Новый заголовок'
zetto tag add "$note_id" rust
zetto tag remove "$note_id" rust

zetto lint --fresh --format json
zetto index rebuild
zetto doctor
zetto resync --dry-run
zetto resync --apply

zetto import ./old-notes --dry-run
zetto import ./old-notes --apply
zetto export --to-markdown --output ./exported
```

Это проект контракта, не команды уже установленной программы. Значения переменных в примерах — полные ULID. `new --stdin` не запускает редактор; `capture --stdin` всегда сохраняет draft; `new --stdin` при провале публикации возвращает отдельный результат `draft_saved`, ID и путь, а не стирает ввод. `link` добавляет в конец тела каноническую ссылку без переформатирования остального текста; расширенная вставка в определённое место — задача редактора.

### Правила совместимости

- stdout содержит только запрошенные данные; прогресс и предупреждения — stderr.
- `--format json` выдаёт один документ с `schema_version`, `data`, `warnings`, `freshness`; JSONL — записи с версией и типом, завершающая запись содержит итог и полноту. Частичный поток не считается полным успешным ответом.
- Стабильные строковые error codes и rule IDs; текст сообщения может локализоваться. Диагностика ошибок в машинном режиме тоже структурирована.
- Коды завершения: `0` — операция выполнена; `1` — проверка/публикация не пройдена, включая сохранённый draft; `2` — неверный вызов/конфигурация; `3` — конфликт/блокировка; `4` — I/O/восстановление; `130` — прерывание. Сохранение файла с проблемой только индекса — `0` и предупреждение.
- `lint` возвращает `1` при error; `--warnings-as-errors` пригоден для git hook/CI. `search` с нулём результатов возвращает `0` и пустую выдачу, не «ошибку приложения».
- Машинный режим не имеет ANSI; табличный режим использует auto-color; `path --null` возвращает NUL-разделённые пути для безопасной композиции. Несколько ID передаются явными аргументами или документированным NUL-вводом.
- Все запросы имеют детерминированную сортировку с ULID/path как дополнительным ключом и ограничение выдачи. В 1.0 не нужен нестабильный SQL/query DSL.
- `--vault` → `ZETTO_VAULT` → поиск `.zettorc` вверх от cwd → default из ADR-0001. Пользовательские параметры CLI имеют высший приоритет. Нахождение хранилища не разрешает запускать код из его конфигурации.

Формат данных, CLI и JSON после 1.0 меняются по опубликованным правилам совместимости. Внутренние Rust-типы пока не объявляются стабильным SDK. Completion и man page строятся из одного определения CLI, чтобы не расходиться с бинарником.

## 10. Импорт, экспорт и git

Импорт работает в два прохода: сначала создаёт таблицу исходный файл/старый ID → новый ULID, затем переводит ссылки через Markdown-парсер. Нельзя менять ссылки заменой строк по всему файлу: примеры кода не должны превратиться в реальные связи.

`--dry-run` выдаёт список создаваемых файлов, коллизии, неподдержанные конструкции и ссылки, которым не нашлось цели. До `--apply` этот план сохраняется. Исходное дерево никогда не меняется; импорт создаёт новое содержимое, сомнительные заметки остаются в inbox. Повторный запуск использует сохранённое сопоставление и не дублирует уже созданные заметки. UUID-формат старого прототипа — отдельный входной адаптер, а не второй нативный формат zetto.

Существующий Obsidian vault можно импортировать, но 1.0 не обещает двустороннюю совместимость с ним. `[[ULID]]` не обязан разрешаться Obsidian по alias при имени `<ULID>-<slug>.md`; это проверяемое поведение конкретного инструмента, не наше обещание. Неподдержанные embeds/anchors/block refs сохраняются с отчётом, а не молча отбрасываются.

Экспорт копирует заметки в отдельный каталог и преобразует канонические внутренние ссылки в относительные Markdown-ссылки по карте экспорта. Вложения копируются без выхода за корень; пропущенные/неоднозначные ссылки перечисляются. Исходные файлы не меняются, существующий каталог без явной политики перезаписи не затирается. В 1.0 достаточно обычного Markdown; HTML-сайт/PDF — внешние инструменты.

zetto не выполняет git commit/push/pull автоматически. Предлагает пример pre-commit hook с `lint` и показывает понятный статус конфликта, если файл содержит маркеры неразрешённого merge. Не разрешает управляемую перезапись конфликтного файла. Во время внешнего `git checkout/pull` нет общей транзакции с zetto: дождаться сверки и разрешить конфликт прежде, чем менять затронутую заметку.

Встроенное удаление в 1.0 не вводится: ADR-0002 относит удаление к пользовательскому git workflow. В TUI можно показать путь и обратные ссылки перед ручным удалением. Автоматическое удаление истории не является функцией менеджера заметок.

## 11. Настройки, доверие и диагностика

Пользовательские настройки: XDG `zetto/config.toml`; темы и клавиши — отдельные пользовательские TOML. `.zettorc` содержит только переносимые настройки хранилища: формат/каталоги, root ID, lint. Локальный UI-state и логи хранятся в XDG state. Порядок приоритетов: CLI → пользовательские настройки → переносимые настройки, с явно разнесёнными непересекающимися областями; список параметров задаёт, где разрешено каждое поле.

Чужое хранилище — недоверенные данные. Его конфигурация не задаёт shell hooks, команды редактора, путь логов за корнем или исполнение шаблонов. Шаблоны — текст с небольшим фиксированным набором подстановок, без Tera/произвольных выражений до реальной потребности. Символические ссылки за корень не обходятся при индексировании, записи и экспорте; относительные пути нормализуются и проверяются перед доступом. При управляемой записи проверяется реальное расположение родителя, а не только строковый префикс.

YAML не включает файлы и не выполняет пользовательские теги; задаются бюджеты вложенности/размера. Повреждённый или слишком большой файл остаётся видимым с диагностикой и доступен raw-чтению/редактору, а не исчезает из результатов без объяснения. Raw-вывод в TTY экранирует управляющие символы; pipe raw выдаёт исходные байты как запрошенные данные.

`doctor` проверяет формат, права, текущую версию SQLite, доступность редактора, незавершённые операции, конфликты ID и состояние индекса. Диагностика не записывает полные тела/запросы поиска в логи по умолчанию. `--debug` даёт длительности и коды ошибок; экспорт диагностического отчёта — явное действие с предварительным просмотром путей. Никакой телеметрии по умолчанию.

## 12. Уточнения принятых ADR перед кодом

| Основание | Проблема текущего текста | Предлагаемое новое решение |
|---|---|---|
| ADR-0002, slug lifecycle | Чтение может автоматически переименовать файл; различаются mismatch ID и mismatch slug | Чтение не меняет заметки; разные диагностики; retitle/resync явные |
| ADR-0002/0003, ULID | Regex/частичный timestamp-check не равен полной проверке ULID | Полный разбор и проверка диапазона через `ulid`, корпус граничных случаев |
| ADR-0003/0004, resolver | В одном документе не-ULID прекращает resolve, в другом после него должны работать aliases; saturation одновременно отключает правило и выбирает первого | Один опубликованный порядок passes; ambiguous не разрешается автоматически |
| ADR-0004, YAML writer | «Verbatim unknown» и byte-for-byte round-trip не гарантируются обычным deserialize/serialize | Для неизменённого файла сохранять исходные байты; управляемая запись известных полей канонизируется один раз, затем идемпотентна; нормализация unknown/comments явно показана и не называется verbatim |
| ADR-0002/0004, YAML dependency | В ADR фигурирует архивированный `serde_yaml` | Проверить `serde-saphyr` на корпусе, зафиксировать выбор новым ADR; не считать любой fork автоматически безопасной заменой |
| ADR-0004, optional timestamps | Типизированное чтение timestamp может остановить десериализацию раньше обещанного warn | Сначала разобрать сырые значения, затем отдельно валидировать required/optional; некорректное optional сохранять и диагностировать |
| ADR-0004, concurrent writes | Single-writer assumption не описывает CLI при открытом TUI | Краткие межпроцессные блокировки, рабочие копии редактора, хеши, recovery; гарантии для внешних редакторов ограничены |
| ADR-0004, `updated` | Индекс не должен становиться единственным источником авторского timestamp; фоновая правка заметок создаёт шум git | zetto-managed edit обновляет по изменению тела; внешние правки сами по себе не переписывают metadata; rebuild не меняет пользовательские timestamps |
| STRATEGY, capture | Сохранение мысли и публикация связанного знания объединены в одну цель | Capture/prep split, отдельные метрики, проверяемая доля опубликованных сирот и возраст inbox |

Существующие ADR остаются в истории и получают `Superseded`/ссылки только после принятия новых решений. Этот документ не является молчаливой отменой контрактов. [Upstream serde-yaml](https://github.com/dtolnay/serde-yaml) действительно архивирован; [serde-saphyr](https://docs.rs/serde-saphyr/latest/serde_saphyr/) рассматривается как кандидат, а не уже проверенная замена для полного корпуса zetto.

До начала реализации нужно закрыть четыре пакета решений: (1) формат/layout/resolver и перечисленные расхождения; (2) запись/восстановление/индекс; (3) CLI/TUI и capture/publish; (4) границы 1.0 и проверка выпуска. Не требуется двадцать отдельных исследовательских циклов: тесно связанные вопросы фиксируются вместе, остальные уточняются работающими срезами.

## 13. Проверяемые цели быстродействия

**Числа ниже — предлагаемые критерии, не замеры.** Исходный корпус: 5 000 заметок, медиана тела около 4 KiB, смешанный русский/английский текст, 3–10 связей на заметку; стресс — 50 000 заметок и несколько крупных файлов. Аппаратная конфигурация и режим кэша ОС записываются рядом с каждым результатом. «Первый rebuild», «запуск с существующим индексом» и «cached-запрос» — разные измерения.

| Операция на основном корпусе | Цель |
|---|---|
| TUI: первый полезный кадр с готовым индексом | p95 < 200 ms; свежесть может ещё проверяться |
| CLI: обычный запрос со сверкой metadata | p95 < 500 ms; отдельно видно O(N) обхода |
| CLI: явно cached-запрос | p95 < 100 ms |
| Быстрый выбор заголовка | p95 < 50 ms после очередного ввода |
| FTS после готового индекса | p95 < 150 ms |
| Подтверждение capture, включая durable write | p95 < 300 ms на локальном SSD |
| UI после клавиши | p95 < 50 ms; индексация не блокирует кадр |
| Полный rebuild | первоначальная цель < 5 s; уточняется первой реализацией |
| Память TUI | ориентир RSS < 100 MiB на основном корпусе |
| Idle | нет непрерывной перерисовки; CPU измеряется относительно пустого terminal-loop |

При провале сначала измеряются этапы, затем меняется реализация или честно пересматривается цель. На 50k не обещаем те же времена полного обхода; требуем отменяемость, правильность и отсутствие зависания UI. Качество поиска проверяется отдельным корпусом ожидаемых запросов, а не только скоростью.

## 14. Дорога до 1.0

Оценка — порядок величины для одного разработчика с хорошим знанием Rust. Это не срок по договору: уточняем после первых двух срезов. Ориентир **18–28 недель сосредоточенной работы**, при работе вечерами календарный срок больше. Этапы завершаются проверяемым пользовательским результатом.

| Этап | Содержание | Условие перехода | Объём |
|---|---|---|---|
| 0. Контракт | Новые ADR по спорным местам, format-v1 draft, примеры CLI, макет TUI, корпус данных | Однозначно описаны ID/resolve/запись/черновик; список 1.0 ограничен | 1–2 недели |
| 1. Рабочий срез v0.1 | `init → capture → edit → link → publish → show`; безопасная запись, простой индекс; минимальный Ratatui-экран библиотеки и предпросмотра | В одном хранилище действительно проходит ежедневный цикл через CLI и TUI; индекс удаляем без потери заметок | 3–4 недели |
| 2. Поиск и граф v0.2 | Производный SQLite/FTS, backlinks, aliases, сверка, потоки задач, параллельный CLI | Ручное изменение/rename/git-переключение отражается в выдаче; нет зависания TUI и молчаливой потери при конфликте | 3–4 недели |
| 3. Основной TUI v0.3 | Финальная Library/Focus, inbox/prep, палитра, история, адаптивный layout, основной визуальный стиль | Можно неделю работать без обращения к внутренностям проекта и без обязательных внешних picker-ов | 3–4 недели |
| 4. Методология v0.4 | Общие диагностики, presets, корректные исключения, root bootstrap, понятные действия исправления | Одинаковые входные данные дают одинаковые причины/уровни в CLI и TUI; невалидная публикация сохраняет draft | 2–3 недели |
| 5. Переносимость v0.5 | Импорт Markdown/старого прототипа, экспорт, вложения, завершение recovery/doctor, JSON, completion/man | Round-trip экспортируемых связей проверен; прерванный импорт безопасно возобновляется; внешние исходники неизменны | 2–3 недели |
| 6. Beta / RC | Темы, клавиши, Unicode/SSH/tmux/macOS, устранение сбоев, измерения, binary releases, upgrade/downgrade | Реальное ежедневное использование 2–4 недели; опубликованы ограничения; проходят release gates | 3–6 недель |
| 7. v1.0 | Заморозка публичных контрактов, руководство, стабильные сборки и примеры | Нет открытых блокирующих дефектов данных/терминала/совместимости; выпуск ставится и обновляется из опубликованных пакетов | 1–2 недели |

Широкий UI не откладывается до готовности всех внутренних решений: на этапе 1 уже есть настоящий TUI на тех же операциях. Визуальная система появляется в работающем приложении, проверяется ежедневным использованием и дорабатывается к beta. Дополнительные экраны не мешают сначала проверить самый важный цикл.

При нехватке времени до 1.0 можно уменьшить число тем, оставить граф только списком соседей и упростить встроенный capture-input до многострочной вставки плюс `$EDITOR`. Нельзя вырезать безопасное сохранение, полноценный CLI, доступ с клавиатуры, восстановление и гарантии формата.

## 15. Проверка готовности и выпуск

### Корпус и проверки

- Контрактные примеры: корректный/ошибочный ULID, overflow, кириллица/пустой slug, scalar tags, unknown fields, неверный timestamp, duplicate YAML keys, код с wikilinks, отсутствующие и неоднозначные цели.
- Проверка writer: неизменённое чтение не меняет файл; канонизация после первого управляемого изменения стабилизируется; тело сохраняется побайтно; потеря комментариев/форматирования не маскируется обещанием lossless.
- Интеграционные тесты реальных файлов: disk-full/permission denied, конфликт редактора, duplicate ID, прерывание до/после rename, индекс недоступен после успешного save, два CLI и TUI одновременно.
- Проверка index: полный rebuild и инкрементальная сверка дают один граф/диагностики; переименование alias/удаление цели инвалидирует зависимые рёбра; сохранённый mtime покрывает `--fresh`.
- Проверка терминала через PTY: вход/выход, паника, resize, paste, редактор с ненулевым кодом, Ctrl-C и Unix suspend/resume. Снимки виджетов Ratatui проверяют состояние и layout, а не один красивый скриншот.
- Машинный контракт: stdin без TTY, отсутствие ANSI в JSON, коды ошибок, частичный JSONL, Unicode и NUL-пути, пустые результаты, отсутствие скрытых вопросов.
- Fuzzing границ YAML/Markdown/resolver — ограниченный по времени CI и более длинный периодический прогон. Случайные данные не должны вызывать запись за корень или panic.

### Release gates

1. Чистая установка на Linux x86_64/aarch64 и macOS Intel/Apple Silicon, запуск без установленного rg/fzf; `$EDITOR` проверяется при редактировании, не при `list`.
2. Проверенная матрица терминалов: минимум один простой терминал, Kitty/Alacritty/WezTerm или эквивалентные целевые среды, tmux, SSH, 16 цветов, `NO_COLOR`, отсутствие Nerd Font. Это план проверки, не заявленная совместимость без прогонов.
3. Заметка после успешного capture читается обычным `cat`; удаление индекса не удаляет заметку; восстановление незавершённой операции демонстрируется на тестовом vault.
4. Все критерии повреждения/потери данных и блокирующие дефекты терминала закрыты; результаты performance-корпуса опубликованы с аппаратной средой.
5. Релизный lockfile, проверка лицензий и известных advisories, форматирование, clippy, тесты; встроенный SQLite/FTS5 реально проверены исполняемым smoke-test.
6. GitHub Releases: бинарники, checksums, проверяемое происхождение сборки; `cargo install` как дополнительный канал. Homebrew/AUR — после воспроизводимой основной сборки, не отдельные варианты поведения.
7. Документация: короткий старт, все команды, клавиши/темы, format-v1, импорт/экспорт, резервное копирование/recovery, ограничения внешнего редактирования и downgrade. Отказ от downgrade при новой версии формата должен быть понятным.

CI собирает и проверяет изменения; публикация релиза — отдельное явное действие владельца. В 1.0 нет обязательного auto-update и скрытых сетевых проверок версии при запуске.

## 16. Нерешённые вопросы и точки пересмотра

1. **Рабочая копия редактора:** проверить неудобство относительных ссылок/плагинов Neovim. Если оно неприемлемо, предложить явный direct-edit с резервированием исходника и ослабленной гарантией, отдельно от безопасного режима; не молча подменять модель.
2. **YAML-парсер и writer:** кандидат проверяется на корпусе до выбора; preservation неизвестных YAML-конструкций требует честной спецификации. Это основной технический спайк этапа 0.
3. **Порог масштаба:** если stat-обход 5k файлов не проходит бюджет, сначала измерить файловую систему и способы сверки. Новая стратегия свежести должна явно сообщать, какую гарантию она ослабляет.
4. **Строгость методологии:** проверить на собственном ежедневном использовании, не ведёт ли inbox к отказу от публикации. Менять default после наблюдения, а не подгонять плотность ссылок искусственно.
5. **Распространение:** доступность имени в реестрах и подпись пакетов проверяются непосредственно перед публикацией; старые записи ADR не доказывают текущую доступность.
