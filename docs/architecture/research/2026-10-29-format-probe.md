# Этап 0: проверка YAML-кандидата и корпусов

Автор: Igor Kramar. Дата: 2026-10-29.

## Цель и граница

Проверить конкретную неопределённость [предложения 1.0](2026-10-29-zetto-1.0-design.md):
пригоден ли `serde-saphyr` для чтения frontmatter с неизвестными вложенными
полями и независимыми ошибками обязательных/необязательных полей.
Это проверочный пакет, не универсальное ядро приложения.

## Среда и воспроизведение

Linux x86_64, Rust 1.99.1, Cargo 1.99.1. В стенде заявлен `rust-version = 1.89`
по [MSRV serde-saphyr](https://docs.rs/serde-saphyr/2.0.0/serde_saphyr/),
но сборка именно компилятором 1.89 в этом эксперименте не проверялась.
Не переносить MSRV стенда на весь будущий набор зависимостей приложения.
Версии зафиксированы в [Cargo.lock](../../../tools/format-probe/Cargo.lock):
serde-saphyr 2.0.0, ulid 1.2.1, chrono 0.4.45, serde_json 1.0.154.

```sh
work-run -- cargo test --locked --manifest-path tools/format-probe/Cargo.toml
work-run -- cargo fmt --check --manifest-path tools/format-probe/Cargo.toml
work-run -- cargo clippy --locked --manifest-path tools/format-probe/Cargo.toml --all-targets -- -D warnings
work-run -- python3 tools/corpus.py --self-check
```

## Наблюдаемые результаты

Корпус из 32 случаев проходит одним параметризованным тестом.
Для каждого допустимого ввода проверяются диагностики, ожидаемое полное дерево
(если задано), parse→serialize→parse equality и стабильность повторной записи.

| Группа | Наблюдение |
|---|---|
| UTF-8, кавычки, CRLF, literal/folded строки | Прочитаны с ожидаемыми значениями |
| Неизвестные вложенные mapping/list/null/bool/number | Сохранены после повторной сериализации |
| Anchors, aliases, merge keys | Сохранены результирующие значения; не исходный синтаксис |
| `no/yes/on/off` | Остались строками при strict_booleans |
| Неверные tags/aliases/created/updated | Валидные id/title и неизвестные значения остаются доступны; отдельные диагностики |
| Missing/неверный тип id/title, empty title | Разные результаты проверок после YAML-разбора |
| Duplicate key, syntax, multiple documents, custom tag, include, non-finite, complex key, recursive alias | Отказ без принятия испорченного дерева |
| Lowercase/запрещённые символы ULID | Отказ прикладной проверки |
| Overflow ULID | Обнаружен пробел библиотечной проверки; добавлен самостоятельный верхний предел |
| Числовые/строковые YAML-ключи | Обнаружено схлопывание ключей в Value; `no_schema: true` запрещает coercion, строковые числовые ключи требуют кавычек |
| tags/aliases корректными и пустыми списками | Допустимы и сохраняются после записи |

Исходный прогон упал на `ulid-overflow`: `ulid 1.2.1` успешно декодировал
`ZZZZZZZZZZZZZZZZZZZZZZZZZZ`, прикладная проверка не вернула ошибку.
После добавления `first byte <= '7'` тот же тест проходит. Эта проверка
обязательна для будущего parser/resolver; регулярного алфавита и одного
`parse::<Ulid>()` недостаточно. Это согласуется с
[128-битным пределом ULID](https://github.com/ulid/spec#overflow-errors-when-parsing-base32-strings).

Ревью отдельно воспроизвело `x-extra: {1: one, '1': two}` → только
`{"x-extra":{"1":"two"}}`: значение `one` было потеряно до round-trip.
Добавленный rejected-тест сначала упал с этим деревом. Включённый
`no_schema: true` запретил преобразование числового ключа в строку;
добавлены decimal/hex/boolean/null коллизии и положительный случай ключей
в кавычках. Итоговые 32 случая проходят. Это ограничение YAML-профиля,
а не обещание сохранить произвольные ключи YAML.

Результат выбора: **кандидат прошёл проверенный YAML-профиль**, его можно
предложить в ADR-0005. Не заявляется произвольный YAML round-trip,
сохранение комментариев/порядка/anchors, реализация файлового writer,
защита всех ресурсных границ или fuzzing. Все ошибки полей проверяются
после разбора в дерево: это принципиально отличается от derive struct,
где первая ошибка optional-поля может прекратить всю десериализацию.

## Корпуса

Малый vault: 8 заметок, 5 разрешённых рёбер. Некорректный vault: 9 файлов.
Оба сохранены вместе с manifest ожидаемых результатов и SHA-256.
28 resolver-сценариев и 2 Markdown range-примера — ожидаемые результаты
для реализации v0.1/v0.2, не выдаются за выполненный resolver-тест.

Большие корпуса **фактически сгенерированы и проверены по каждому хешу**:
5 000 заметок / 4 999 рёбер и 50 000 / 49 999. Лежат в игнорируемом
`.generated/`; их можно воспроизвести через [инструкцию](../../../tests/corpus/README.md).
Это измерение состава тестовых данных. Производительность zetto не измерялась:
приложение ещё не реализовано. Времена генерации не подменяют startup/search.
