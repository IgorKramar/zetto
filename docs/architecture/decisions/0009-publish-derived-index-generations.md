# ADR-0009: Публиковать производный индекс согласованными поколениями

- **Дата**: 2026-10-30
- **Статус**: Accepted — реализация выбранного владельцем направления v0.2
- **Автор**: Igor Kramar

## Контекст

[План v0.2](../../plans/2026-10-30-v0.2-search-index-concurrency.md) реализует
SQLite/FTS5 и несколько процессов из плана владельца. ADR-0005–0008 сохраняют
приоритет файлов, неоднозначность дубликатов и независимое recovery.
Обход v0.1 парсит все тела; resolver выполняет поиск по всему каталогу
на каждую ссылку. Нельзя держать SQLite write transaction во время обхода,
редактора или ожидания клавиши. Тела всех заметок не нужны UI-каталогу.

## Решение

Использовать `rusqlite` с bundled SQLite/FTS5, WAL и ограниченным busy timeout.
База размещается в приватном XDG cache по хешу канонического vault.
File key — внутреннее число, path уникален, ULID допускает дубликаты.
Согласованные files/links/tags/aliases/diagnostics/FTS и generation
публикуются одной транзакцией. Обход и разбор идут до write transaction;
при её получении сравнивается generation, проигравший процесс повторяет
сверку ограниченное число раз. Rebuild обновляет ту же базу без unlink.

Stat сравнивает наличие/размер/mtime, full проверяет содержимое каждого
файла, cached читает прежнее поколение без обхода. Перед/после чтения
проверяется состояние файла; нестабильное чтение даёт диагностику.
Каталог содержит метаданные без тел; preview загружается отдельно.
Общий resolver использует карты ID/path/alias/stem. После изменений
повторно разрешаются все ссылки, включая прежние unresolved.

После подтверждённой записи Markdown короткая транзакция ставит dirty
marker, сохраняя прежний согласованный snapshot до следующей сверки.
Отказ индекса даёт index_stale и не отменяет saved:true. Capture не ждёт
полного графа. Проверки изменения и файловое recovery доступны без базы.
Ограниченный worker выполняет I/O для TUI; request ID и отмена защищают
от устаревшей выдачи. Notify сообщает о необходимости сверки; ошибки,
потеря событий и периодическая проверка приводят к повторному обходу.

## Последствия

Независимые CLI используют общий индекс без демона. Ошибочный файл остаётся
видимым, конфликт идентичности представим. Сверка остаётся O(N) stat,
повторное разрешение — проход по всем ссылкам. Cached может отставать;
режим и dirty warning видны в ответе. SQLite не создаёт транзакции с
внешним редактором и не заменяет backup.

## Рассмотренные альтернативы

1. **Оставить полный обход в памяти.** Проверен v0.1, но повторяет парсинг
   и хранит все тела, не даёт FTS и дешёвых повторных запросов.
2. **Демон — единственный владелец индекса.** Упрощает сериализацию,
   добавляет обязательный процесс и протокол; исключён планом 1.0.
3. **Немедленно обновлять только строку изменённого файла.** Быстро,
   но новый alias/дубликат может изменить чужие рёбра. Dirty marker
   сохраняет целостное старое поколение без сложного staging.

## Проверенные источники

Исследование 2026-10-30: `cargo info` подтвердил MSRV rusqlite 0.41.1
1.89 и notify 8.2.0 1.77. [Rusqlite](https://github.com/rusqlite/rusqlite)
поддерживает bundled сборку; фактические sqlite_version/FTS5 проверяются
тестом приложения. [SQLite WAL](https://www.sqlite.org/wal.html) допускает
SQLITE_BUSY, поэтому ожидание ограничено. [FTS5](https://www.sqlite.org/fts5.html)
ранжирует лучшие bm25 меньшими значениями.
[Notify](https://docs.rs/notify/8.2.0/notify/) описывает разные события
редакторов и потерю событий; watcher не считается источником истины.
